#### 目的

#### 実測（RTX 3060 Laptop、640px、batch 1、conf 0.25、60回の中央値）

| モデル | 推論 | 検出内容 | VRAM |
|---|---|---|---|
| yolov8n（旧） | 6.6ms | bus 0.87、**誤検出 stop sign 0.26**、tie 0.29 | 0.03GB |
| yolo26n | 10.0ms | bus 0.92、誤検出なし、tie 0.53 | 0.07GB |
| **yolo26s（採用）** | 11.0ms | bus 0.93、tie 0.88、person 0.94 | 0.13GB |
| yolo26m | 17〜22ms | bus 0.94、person 0.96 | 0.24GB |

#### 「爆速」は GPU では成立しなかった

内訳を取ると、
```
yolov8n : 推論 6.4ms + NMS 1.1ms
yolo26n : 推論 11.0ms + NMS 0.4ms
```
NMS-free の効果は出ている（1.1 → 0.4ms）が、それを上回ってバックボーンが重い。
YOLO26 の速度優位は **CPU 推論と end-to-end エクスポート**の話であり、
CUDA GPU で nano クラスを回す本件の条件では効かない。精度向上は明確。

なお計測初回に「26s が 26n より速い」と出たが、60回計測で消えたためノイズ。
n=10.0ms < s=11.0ms が正しい。

#### 採用理由: yolo26s
26n より +1.0ms のみで COCO mAP 40.1 → 47.8。アプリは YOLO を 15 ティックに
1回しか回さないため +4.4ms（対 v8n）は体感に出ない。VRAM も 0.13GB。

- `models/yolo26n.pt`、`models/yolo26s.pt` を追加（旧 v8 系は削除せず保持）

- `requirements-yolo.txt`: `ultralytics>=8.0.0` → `==8.4.41`（YOLO26 は 8.3.222 以降が必要）
- コード変更は**不要**。呼び出しは `YOLO(path)` と `predict(bgr, conf=...)` のみで、
  `iou` を渡していないため NMS-free 化の影響を受けない

#### 4. YOLO26 採用後の速度低下と、その解消（追記）

#### 症状
ユーザー報告「yolo26s だいぶ処理が遅くなった。v8 の方がリアルタイム性が高かった」。

#### 「s を n に下げれば戻る」は誤り（実測で否定）

```
yolov8n 推論  7.3ms
yolo26n 推論 11.7ms
yolo26s 推論 11.9ms   ← n と s の差は 0.2ms
```

`imgsz` 640→448 でもほぼ不変、`half=True` はむしろ遅化（14.9→17.0ms）。
FLOPs ではなく**カーネル起動回数で律速**しており、モデルを小さくしても戻らない。

#### 真因: ティックの二重発火

`robot_v2.py` は 33ms（30FPS）ティック。`_run_diff_yolo` と `_run_raw_yolo` が
どちらも「15ティックごと」だったため、15回に1回のティックで YOLO を2回実行していた。

実経路（1280x720、`StreamingYoloPipeline.process` ＋ `predict_frame`）の実測:

| 構成 | 差分ティック | 生ティック | 同時発火 | 33ms予算 |
|---|---|---|---|---|
| yolov8n | 15.3ms | 10.6ms | **25.9ms** | 辛うじて収まる |
| yolo26s | 19.2ms | 13.3ms | **32.5ms** | 超過寸前 → 描画が詰まる |

v8n 時代から存在した設計上の無駄が、YOLO26 の +4ms で顕在化した形。
モデル差そのものが体感の原因ではない。

#### 対応

`_run_raw_yolo` に半周期のオフセットを入れ、2つの YOLO を別ティックへ分離。

```python
self._raw_yolo_offset_ticks = self._raw_yolo_every_ticks // 2
...
offset_tick = self._tick_count + self._raw_yolo_offset_ticks
if offset_tick % self._raw_yolo_every_ticks != 0:
```

差分 = 0,15,30… / 生 = 8,23,38… で衝突ゼロ（120ティック検証済み）。
更新頻度は変わらず、タイミングが半周期ずれるだけ。

| | ピークティック |
|---|---|
| v8n・同時発火（従来） | 25.9ms |
| yolo26s・同時発火（修正前） | 32.5ms |
| **yolo26s・ずらし（修正後）** | **19.2ms** |

従来の v8n より 26% 速く、精度は YOLO26 のまま。

`robot.py`（v1）にも同じ二重発火があったため、ユーザー了承のうえ同じ修正を適用。
両ファイルとも `ruff` 通過、`pytest` 33 passed。

#### 検討したが採用しなかった案
- **バッチ化**（2枚を1回の `predict` に）: ピーク 15.0ms と僅かに速いが、
  `StreamingYoloPipeline.process` が差分計算と推論を内包しているため、
  2モジュールにまたがる構造変更が必要。効果差が小さいので見送り。
- **TensorRT / ONNX エクスポート**: カーネル起動律速には効くはずだが、
  変更量が大きく、Ultralytics の AGPL 論点にも触れるため保留。

#### 6. 追従性の改善：計測基盤・実時間スケジュール・レート引き上げ（追記）

#### 現状把握
ユーザー報告「さっきより遅い。特に動きに追従できていない」。

`_FRAME_INTERVAL_MS = 33`、`raw/diff_yolo_every_ticks = 15` のため、
**YOLO は 495ms に1回（約2Hz）**。一方、5章で追加した生フレームの枠描画は
そのキャッシュを**毎ティック（30Hz）**描いていた。

#### 要因

**要因1: 検出2Hz、描画30Hz → 枠が最大495ms古い**
秒速1mで歩く人なら枠は約0.5m後方を追う。5章の変更が既存の設計を可視化しただけで、
枠そのものが原因ではない。

**要因2: `_tick_count` が GPU ビジー中に進まない（不良と判断）**

```python
if not self._gpu_busy():
    self._tick_count += 1   # ← ビジー中は加算されない
```

不良と判断した根拠（データフローを追い切った上で）:
1. **名前と挙動の不一致**: 変数名は `_tick_count`（QTimer のティック数。GPU 状態に
   無関係に 33ms ごとに発生）、設定キーは `*_every_ticks`（=「Nティックごと」）。
   実際は「非ビジーティックを N 回数えたら」で、所要時間が確定しない。
2. **同一クラス内の不整合**: 実況の間引き `_request_caption` は `time.monotonic()`
   と秒で制御している。YOLO だけが別単位。
3. **消費箇所は2つだけ**で、`_on_stop` でリセットもされない。スケジューリングの
   基準として設計された形跡がない。

意図的と読める余地（空き GPU 時間に対する稼働率を一定に保つ）はあるが、
その目的なら実時間スケジュール＋ビジー時スキップで達成でき、かつ間隔が予測可能になる。
見守り用途で検出間隔が「喋った量」で伸縮するのは正しくない。

**要因3: 実機の FPS を測る手段が無かった**
`StatsWidget` は配置されているのに `update_stats()` が一度も呼ばれておらず、
FPS 表示は常に `--`。合成フレームの単体計測だけで判断していたのは進め方の不備。

**第1段階: 計測の可視化**

**第2段階: レート引き上げ**

  `_speak()` の中で `_stop_tts_worker()`（参照の破棄）を通った直後にあたる。

#### 3. 要因（有力候補）

Qt6Core が `qFatal()` を出す代表例が
**"QThread: Destroyed while thread is still running"**。
本アプリのワーカーは `QThread` を **Python の変数だけで保持**しており、
参照を捨てた瞬間に C++ オブジェクトが破棄される。捨てるのが早すぎる箇所が2つ:

1. `robot/chat_panel.py` `_finish_worker()` … `completed` / `failed` から呼ばれて
   `self._worker = None`。両シグナルは `run()` の末尾で emit されるため、
   スロット実行時にスレッドがまだ終わっていない可能性がある。会話のたびに通る。
2. `robot_v2.py` `_stop_tts_worker()` … `wait(2000)` がタイムアウトしても
   `self._tts_worker = None` にする。合成が2秒を超えると実行中スレッドを破棄する。

どちらも「たいてい間に合うが、たまに負ける」競合なので、時々落ちる症状と一致する。

**断定はしていない。** 今回の実行では WER イベントも stderr のメッセージも
残っておらず、機序の証明には至っていない。7/14 の記録も同一アプリとは限らない。
以下は「この競合を消す」対応であり、再発の有無で確認する。

#### 4. 対応（Qt の定石に統一）

ワーカー生成時に:

- `parent` を渡して **C++ 側に所有権**を移す。Python の参照が消えても破棄されない。
- `finished` → `deleteLater()`。スレッド終了後に解放される。
- 参照のクリアは `completed` ではなく `finished` で行う。

| ファイル | 変更 |
|---|---|
| `robot/chat_panel.py` | `LlmWorker(..., self)`、`finished` → `_release_worker` / `deleteLater`。`_finish_worker()` は UI 解除のみに縮小 |
| `robot_v2.py` | `TtsWorker(..., self)` / `CaptionWorker(..., self)`、両方に `finished` → `deleteLater` |
| `robot_v2.py` | `_on_tts_thread_finished()` に「追跡中のワーカーがまだ動いていれば無視」のガード。TTS は複数が重なり得るため |
| `robot_v2.py` | `_TTS_STOP_WAIT_MS = 2000` を定数化 |

副作用: `is_busy()` がスレッド終了まで True のままになる（数ミリ秒長い）。
GPU の直列化がわずかに安全側に振れるだけで、処理速度への影響はない。
