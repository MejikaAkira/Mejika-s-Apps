## リアルタイム動画差分検出の提案（LogSense_v5）

### 1. アーキテクチャ設計

#### 基本フロー
```
動画入力 → フレーム抽出 → 位置補正 → 差分計算 → 可視化 → 出力
```

#### 処理パイプライン
- マルチスレッド/マルチプロセスで並列処理
- フレームバッファリングで遅延を最小化
- GPU/CPUハイブリッド最適化を活用

### 2. 技術的な課題と解決策

#### 課題1: 処理速度
- 現状: 静止画で0.3-0.8秒/枚
- 目標: 30fps（約33ms/フレーム）または60fps（約16ms/フレーム）

解決策:
- フレーム間差分の最適化（前フレームとの差分のみ計算）
- 位置補正の簡略化（前フレームのホモグラフィを再利用）
- 解像度の動的調整（処理負荷に応じて解像度を下げる）
- GPU処理の最大化（位置補正、差分計算をGPUで実行）

#### 課題2: 位置補正の高速化
- 現状: ORB特徴点検出で200-300ms
- 目標: 10ms以下

解決策:
- フレーム間の位置補正を簡略化（オプティカルフローを使用）
- 特徴点検出の間引き（Nフレームに1回のみ）
- 前フレームのホモグラフィを再利用（微小な動きのみ補正）
- カメラ固定前提なら位置補正をスキップ

#### 課題3: メモリ管理
- 動画は大量のデータを扱うため、メモリ効率が重要

解決策:
- フレームバッファリング（最新Nフレームのみ保持）
- メモリプール（フレームバッファの再利用）
- ストリーミング処理（フレーム単位で処理）
- メモリ効率化: 直前のフレームとの比較のため、`base_frame`は参照を保持するだけでOK（コピー不要）
- メモリ効率化: 直前のフレームとの比較のため、`base_frame`は参照を保持するだけでOK（コピー不要）

#### 課題4: 差分の可視化
- リアルタイムで差分を表示する必要がある

解決策:
- OpenCVの`cv2.imshow`でリアルタイム表示
- 差分の可視化オプション（ハイライト、マスク、オーバーレイ）
- 差分の統計情報表示（差分ピクセル数、変化率など）

## 8. 実装設計の決定事項（議論結果）

### 8.1 ファイル構成

**決定事項:**
新規ファイルで実装し、既存の`process/*.py`は編集しない。

**根拠:**
- 既存コードのメンテナンス性を維持
- 新機能と既存機能の分離による保守性向上
- 既存の静止画処理に影響を与えない

**ファイル構成:**
```
realtime_video_processor.py    # 処理モジュール（メイン）
realtime_video_gui.py          # GUIモジュール（PyQt）
realtime_video_streaming.py    # ネットワーク送信モジュール
```

### 8.2 処理フロー設計

**決定事項:**
カメラから直接取得したフレームを処理し、表示の遅延は処理に影響させない。

**根拠:**
- 処理と表示を分離することで、表示の遅延が処理性能に影響しない
- フレームバッファによる非同期処理でリアルタイム性を確保
- GUIに表示されたフレームを処理する方式は、表示と処理の同期が必要で複雑になる

**処理フロー:**
```
1. カメラからフレーム取得（独立スレッド）
2. 処理キューに追加
3. 処理スレッドで位置補正・差分計算
4. 結果をフレームバッファに書き込み
5. 保存スレッド（並列）がフレームバッファから読み取り保存（処理をブロックしない）
6. GUIスレッドがフレームバッファから読み取り表示
7. ネットワーク送信ONなら送信
```

**実装の詳細:**
- 処理と保存を並列化することで、保存処理が画像処理をブロックしない
- 各フレーム処理後、`base_frame`を`current_frame`に更新（参照を保持、コピー不要）
- これにより、各フレームは直前のフレームとの差分を計算する

### 8.3 位置補正の最適化

**決定事項:**
指定時間（デフォルト: 0.1秒）は同じホモグラフィ結果を再利用する。再計算タイミングは`config.json`で設定可能。

**根拠:**
- 連続フレーム間では位置補正の変化が小さい
- 特徴点検出（200-300ms）を毎フレーム実行すると30fpsを達成できない
- 0.1秒の再利用で、30fpsの場合約3フレームごとに特徴点検出（約10ms/フレームに削減可能）
- 精度とパフォーマンスのバランスを考慮し、0.1秒（約3フレーム）が適切

**実装:**
- ホモグラフィキャッシュにタイムスタンプを保持
- 指定時間経過したら再計算、それ以外はキャッシュを再利用
- `config.json`の`homography_reuse_seconds`で設定可能（デフォルト: 0.1秒）

### 8.4 差分検出の閾値

**決定事項:**
差分検出の閾値は`config.json`で設定可能。初期値は暫定で、検証して決定。

**設定項目:**
- `threshold_pixels`: 差分ピクセル数の閾値（デフォルト: 5000）
- `threshold_ratio`: 差分ピクセル率の閾値（0.0-1.0、デフォルト: 0.005）
- `noise_threshold`: ノイズ除去の閾値（差分値がこの値未満のピクセルはノイズとして除外、デフォルト: 20）

**根拠:**
- 環境や用途によって適切な閾値が異なる
- 検証しながら調整する必要がある
- configで調整可能にすることで、再実装不要
- ノイズ除去により、カメラノイズによる誤検出を削減

### 8.5 保存方針

**決定事項:**
- 差分が検出されたフレーム: 通常の保存先に保存
- 差分が検出されなかったフレーム: `archive`フォルダに保存

**根拠:**
- 差分検出時のみ保存することで容量を削減（約90%削減可能）
- 差分なしフレームもarchiveに保存することで、後から確認可能
- 最初は短い時間で検証し、閾値を調整

### 8.6 GUI設計

**決定事項:**
PyQtを使用してGUIを実装。GUIモジュールは別ファイル。

**GUI機能:**
- オンライン処理開始/終了ボタン
- 動画録画ON/OFFボタン
- ネットワーク送信ON/OFFボタン
- フレーム表示（元フレーム、差分画像）
- 統計情報表示（FPS、差分ピクセル数、差分率）

**根拠:**
- PyQtは見た目が良く、ボタンUIの実装が容易
- GUIと処理を分離することで、処理性能への影響を最小化
- 別ファイルにすることで、GUIなしでも処理モジュールを実行可能

### 8.7 ネットワーク送信設計

**決定事項:**
ネットワーク送信モジュールは別ファイルで実装。まずUDPで実装し、将来的にWebSocket対応。

**根拠:**
- UDPは低レイテンシでリアルタイム性に適している
- ファイアウォールの問題があるため、将来的にWebSocket対応が必要になる可能性
- プロトコルを抽象化することで、将来的な拡張が容易

**実装方針:**
- プロトコル選択を`config.json`で設定可能（`"udp"` または `"websocket"`）
- まずUDPのみ実装、WebSocketは将来対応
- GUIからのON/OFF制御を受け取る

### 8.8 config.jsonへの設定追加

**決定事項:**
`config.json`に`realtime_video`セクションを追加。

**設定項目:**

### 8.9 画像処理の実装方針

**決定事項:**
画像処理部分は既存の`process/`内の関数のみを使用する。

**使用している既存関数:**
- `resize_to_common_size` (process/alignment_utils.py) - サイズ統一
- `align_images` (process/alignment_utils.py) - 位置補正

**現状の実装:**
- 差分計算は既存の`process/calculate_difference.py`のロジック（209-245行目）をそのまま使用している
- このロジックは画像（`img_base_aligned`, `img_other_aligned`）とマスク（`mask_base_aligned`, `mask_other_aligned`）のみを使用しており、SAM2の結果は使用していない
- `_calculate_difference`メソッド内で既存のロジックをそのまま使用している

**課題:**
- 差分計算ロジックは`process_difference_calculation`関数内に含まれており、関数として抽出されていない
- 理想的には、`calculate_difference.py`に差分計算関数（例: `calculate_image_difference`）を抽出し、それを呼び出すべき
- ただし、既存ファイルを編集しない方針のため、現状は既存のロジックをそのまま使用している

**根拠:**
- 既存の処理ロジックを再利用することで、一貫性とメンテナンス性を確保
- 既存のコードを編集しない方針により、既存機能への影響を回避
- 差分計算ロジックは画像とマスクのみを使用しているため、関数として抽出すれば既存の関数として使用可能

**実装方針（最終決定）:**
- **process内の関数を極力使用**: `resize_to_common_size`, `align_images`など、既存のprocess/内の関数を直接使用
- **差分計算の動画対応**: 動画処理用の差分計算関数は`realtime_video_processor.py`側に追加
  - 既存の`process/calculate_difference.py`のロジック（209-245行目）をそのまま使用
  - 関数名とコメントで動画対応であることを明記
  - 既存の`process_difference_calculation`関数は静止画処理用として維持（既存コードへの影響を回避）
- **メンテナンス性の確保**: 
  - 既存のprocess/内のファイルは編集しない
  - 動画対応の関数は`realtime_video_processor.py`側に追加することで、責務を分離
  - 既存のロジックをそのまま使用することで、一貫性を確保
